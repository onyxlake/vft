# Real RDP through a controlled Hyper-V gateway

Executed on 2026-10-02 (Asia/Shanghai), using commit
`fa7994fef99a692703a2c27a31bfdf0aa6a93e23`. These are real Microsoft RDP transport
tests between a Windows VM sender and the Windows host receiver, with physical screen capture
of the existing RDP client. They are separate from local-window and simulated results. The
network is a local Hyper-V lab with imposed impairment, not a measured WAN deployment.

## Configuration and provisioning

The lab path was:

```text
Windows sender 10.77.1.2
  -> Ubuntu eth0 10.77.1.1 / eth1 10.77.2.2
  -> Windows host 10.77.2.1, displaying the sender through mstsc
  -> local vft-recv-win --auto
```

The separate management addresses `172.30.177.25` (Windows VM) and `172.30.188.17`
(Ubuntu) were used only for SSH/SCP provisioning and test orchestration. The source fixture and
sender executable were uploaded before their transfer runs. The receiver recovered a new output
file from screen pixels; SCP did not deliver the recovered file. SHA-256 was computed on the
remote source and independently on the receiver output before counting a run as successful.

The VM has Windows 11 Pro build 26300; the host is also build 26300, with 16 logical processors
and Rust 1.98.1. Ubuntu
uses kernel `7.0.0-30-generic` and iproute2 `6.19.0`. RDP's actual codec, video bitrate, UDP use
and endpoint DPI settings were not independently established and remain unknown. A TCP RDP
connection between the two lab addresses was established. The sender's fullscreen rectangle
confirmed a 1280 x 720 RDP desktop. The successful cases used windowed 768 x 432 frames:
balanced at 4 physical pixels per cell, robust at 8. The actual local crop is recorded per run.

The default MSVC release executable exited with `0xC0000135` on the fresh VM, which lacked
VC++ runtime DLLs. The working sender was built from the same source with:

```powershell
$env:RUSTFLAGS = '-C target-feature=+crt-static'
cargo build --release -p vft-send-win --target-dir target/remote-static
```

This was a test artifact; the repository's build defaults were not changed. Its SHA-256 was
`4E1E9E700AB3E049680FE7AD2426CD2F98DA259A497D8EF8872E38998807F5CF`.
The sender was started by a temporary Task Scheduler task using the already logged-in user's
interactive token, in RDP session 1. Hidden orchestration launched the sender's visible native
window; no password was saved. Each case stopped only its recorded process and removed its task.
The receiver requested 120 captures/s, but that is not the actual video or unique-frame rate.

Fixtures used `.NET Random(20260930)` in 64 KiB chunks. Expected source hashes:

```text
1 MiB   20AA6FF299998FDD317DE437354EEA93D81B34EC37CF1004B8C3851642CE9CFD
100 MiB 1AC26D6D7497A12D8E86EFF233C8E3604332C967F9DF585C55335134AF4CA552
```

## Network scenarios

Both directions were shaped independently on the Ubuntu lab interfaces, leaving its management
interface `eth2` unchanged. The values below are configured netem limits; they are not measured
video bitrate or video frame loss. Queue overflow can add packet drops beyond configured random
loss. Before/after `tc -s -j qdisc` and link counter snapshots retain the actual queue statistics.

| Scenario | Rate per direction | Delay / jitter per direction | Random packet loss | Queue limit |
| --- | --- | --- | --- | --- |
| Baseline | No imposed limit | None | None imposed | Existing mq/fq_codel |
| Moderate | 5 Mbit/s | 50 / 10 ms | 0.5% | 200 packets |
| Severe | 1 Mbit/s | 100 / 20 ms | 1% | 100 packets |

The configured delay affects each direction; the nominal added round-trip delay is twice the
listed delay. Random netem seeds were generated by the kernel and retained in raw configuration
snapshots, rather than claiming deterministic packet loss. A transient systemd timer reset only
the VFT-owned qdisc handles after ten minutes if orchestration was interrupted. The timer was
rearmed for each shaped case. At batch completion, both interfaces were verified to have their
original mq/fq_codel configuration and no netem root; the timer was removed.

## Verified 1 MiB results

Each matrix case ran once, with a 300 s receiver timeout. Goodput is original bytes divided by
receiver elapsed time, including acquisition, recovery and native SHA verification. KiB/s uses
1024 bytes. Failed runs have zero verified goodput, regardless of accepted symbols.

| Network | Profile / requested FPS / cell | Time, s | Verified KiB/s | Adjacent unique frames/s | Result |
| --- | --- | ---: | ---: | ---: | --- |
| Baseline | Balanced / 5 / 4 px | 51.371 | 19.9 | 4.906 | Independent SHA match |
| Baseline | Balanced / 10 / 4 px | 27.721 | 36.9 | 9.018 | Independent SHA match |
| Baseline | Balanced / 15 / 4 px | 19.691 | 52.0 | 12.696 | Independent SHA match |
| Baseline | Balanced / 30 / 4 px | 19.685 | 52.0 | 18.237 | Independent SHA match |
| Baseline | Robust / 15 / 8 px | 164.440 | 6.2 | 12.600 | Independent SHA match |
| Baseline | Robust / 30 / 8 px | 191.336 | 5.4 | 18.240 | Independent SHA match |
| Moderate | Balanced / 15 / 4 px | 33.224 | 30.8 | 11.046 | Independent SHA match |
| Moderate | Robust / 30 / 8 px | 191.666 | 5.3 | 16.492 | Independent SHA match |
| Severe | Balanced / 15 / 4 px | 300.006 | 0 | 0.360 | Timeout, no verified file |
| Severe | Robust / 30 / 8 px | 273.809 | 3.7 | 11.552 | Independent SHA match |

The severe balanced run accepted 104 symbols but captured long stretches of the same valid
packet. It had no capture decoding rejections, yet could not recover any complete generation.
This demonstrates why zero CRC/capture errors do not establish transport progress. The actual
cause of RDP's stalled updates was not isolated from bandwidth, delay, random loss and queue
overflow. It is not described as a decoder corruption failure or a general failure of 1 Mbit/s.

Robust 30 FPS was slower than robust 15 FPS in this single baseline run. Packet repetition,
missed presentation updates and waiting for repair bursts can offset a higher requested rate;
the requested rate alone is not a performance measurement. More repetitions are needed before
concluding which setting is consistently best.

## Repair-only joining

A separate baseline balanced / 15 FPS / 4 px case started the receiver 25 s after sender
readiness, after the systematic source pass. It independently verified 1 MiB in 33.968 s
after receiver launch, at 30.1 KiB/s. The receiver recorded **zero source frames** and recovered
from repairs alone. This also demonstrated successful transfer after network shaping was removed.

## Sustained 100 MiB baseline

The windowed balanced / 15 FPS / 4 px case independently verified all 104,857,600 bytes in
3499.663 s (58.3 minutes), at **29,962 B/s / 29.3 KiB/s / 30.0 decimal KB/s**. Its output SHA-256
matched the remote source hash above. This is below the 40–100 KB/s target, despite the successful
52.0 KiB/s short-file runs; short-file results did not establish sustained target performance.

The receiver recorded 209,678 captures, 209,612 valid frames, 44,098 adjacent unique frames,
66 capture rejections and one CRC failure. Unique-frame rate was 12.601/s. All 336 generations
completed, with 21,490 accepted symbols, 20 dependent equations and final rank 21,470. Source and
repair capture counts were 101,725 and 100,330 respectively, including duplicates. Accepted-symbol
FEC overhead was 0.000932; this excludes ignored repairs for already completed generations and
must not be read as total transmitted overhead.

During early repairs, 312 generations were complete and about 92.9 MiB had been recovered. The
remaining generations waited for their positions in the sender's round-robin 64-repair bursts.
Thus even sparse missing symbols delayed final verification until late in the repair round.
Low capture rejection alone did not imply a short completion time. The cause of the unobserved
source symbols was not separately measured as network or video frame loss.

Receiver CPU time was 413.984 s and measured peak working set was 174,800,896 bytes (166.7 MiB).
Sender samples recorded 93.984 CPU seconds and a 18,771,968-byte peak (17.9 MiB); these include
the short interval before orchestration stopped it after independent output verification. These
are application process measurements, excluding RDP encoder/client and gateway CPU.

Automatic discovery recorded three scans and two locks at the same `66 119 768 432` rectangle.
Recovery survived a transient decoding interruption and reacquisition. Its cause was uncontrolled;
this is not a deliberate remote movement test. The receiver retained progress across the event.

## Failures and evidence limits

The initial fullscreen 1 MiB balanced / 15 FPS / 8 px run timed out after 180.178 s with zero
accepted data symbols and zero verified goodput. Its diagnostic crop shows the Windows activation
watermark over the data region. Manifests decoded, while populated data frames were repeatedly
rejected. The successful windowed cases placed the complete frame outside that overlay. The
watermark was not disabled. A missing-runtime startup and an orchestration readiness race were
also retained as setup failures; neither is counted as a measured transfer.

These runs add an independently executed real RDP matrix, controlled-network cases, repair-only
joining and a 100 MiB pass. They do not complete the full remote matrix: the requested 8/16 px balanced
and 16 px robust presets, all robust FPS cases, three repetitions per configuration, the remaining
100 MiB configurations, other codecs, deliberate remote movement/occlusion and independently
measured video bitrate remain untested here. The sustained throughput target remains unmet.

Raw fixtures, recovered files, receiver CSV/logs/crop BMPs, remote source hashes, sender metrics,
gateway snapshots and orchestration scripts are retained under ignored
`output/rdp-lab-20261002-040549-e1fc56a1/`. Only small measurement records belong in Git.
Sender CPU/peak-memory samples and receiver process measurements are collected separately.
The [numeric record](remote-rdp-lab-20261002.csv) includes successful and failed transfers, hashes,
configuration, frame/FEC counters, CPU and memory. The two startup failures remain only in raw
diagnostics. Final checks confirmed zero remaining lab sender processes/tasks, no active netem
timer, forwarding still enabled and successful RDP TCP connectivity through the Ubuntu gateway.
